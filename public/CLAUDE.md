# 画面側

> `public/` 配下（`js/` と `css/`）を触るときに読む。
> 全体の地図と横断の約束はルートの `CLAUDE.md` にある。

バニラ JS。フレームワークもビルドも無い。`index.html` が読む `<script>` は1本だけ。

```html
<script type="module" src="js/main.js"></script>
```

ESM なので**読み込み順を人が守る必要はない。** import が解決の順を決める。
素の `<script>` を2本並べていた頃は、順番を入れ替えると立ち上がらず、
トップレベルに同じ名前を2つ置くと SyntaxError で丸ごと落ちていた。その危険は無くなっている。

拡張子は `.js` のままにする。`.mjs` を `public/` に置くと `server.mjs` の `MIME` に無く、
`octet-stream` で返るのでブラウザが module として読まない。

`public/js/` の下に平置き ＋ `timeline/` の1フォルダ。**import は上から下へ一方向にだけ流す。**

**枚数はここに書かない。** 前は「31枚」「33枚」と書いていて、どちらも実態とずれていた
（数える記述はファイルを1枚足すたびに腐る）。下の表が全部を並べているので、
数が知りたければそれを数える。**これは CSS の表にも効く**（あちらも「16枚」で腐っていた）。
逆向きに import したくなったら、置き場所が間違っている。

数値は**取り口を3つに分けてある**（`session.js` の中）。
詳細（2秒ごと）・数値（15秒あけて取り直す）・中央値（5分あけて取り直す）。
同じ `loadDetail()` から並べて撃ち、着いた順に画面へ出す。
詳細の到着を待たない。待つと、キャッシュが効いた詳細のときだけ数値が遅れて出ることになる。

**どれも「選んでいるセッションのものか」を id で突き合わせてから出す。**
選び直した直後は前のセッションの数値が store に残っているので、
突き合わせないと**他人の数字**を数秒のあいだ出し続けることになる。

層3 の中の向きは1本。`detail-wait.js` → `run-ask.js`。
「あなたの番」のパネルに要求が来ているときは、待ちの中身も操作もあちらが持つので、
`waitingBlock()` が丸ごと早期 return する。**逆向きに import しない**（`run-ask.js` は
`WAIT_GUIDE` を知らなくてよい）。`run-view.js` とは向きを作らず、`RUN_OVER` をあえて重複させている
（`run-resume.js` と同じ線）。

層7 の中の向きは2本。`palette.js` → `run-form.js` ／ `palette.js` → `mode.js`。
どちらも片方向で、逆を足すと循環になる。
（ここには長く「`stream.js` → `mode.js`」も並べてあったが、その import は存在しない。
`mode.js` を見ているのは `palette.js` と `main.js` の2つだけ）
`usage-tab.js` と `archive.js` は誰からも import されない（呼ぶのは `main.js` だけ）。
書庫と数値を出す口は `initMode({ onArchive, onUsage })` で外から差す。
`mode.js` があちらを直に import すると、同じ層の中に向きが1本増える。
`palette.js` は層7 のいちばん下流で、誰からも import されない（呼ぶのは `main.js` だけ）。

`archive.js` が層7 なのは `session.js`（層5）を見ているため。

**カードは `list.js` から借りていない。** ここには長く「`buildCard` を借りている」と
書いてあったが、実際には `archive.js` が独自に組んでいた。3つ（一覧・書庫・数値）を
並べて分かったのは、借りられなかった理由のほう ―― 上段に出すもの・札・押したあとが
**問いごとに違う**（状態／日時と大きさ／消費）。
いまは定型だけを `card.js`（層2）に置いて、「何を出すか」は各自が持つ。

`timeline/` の中も同じで、`kinds` `waits` → `search` → `blocks` → `item` → `view` → `index` の順。
**`timeline/` の中のファイルを、外から直に import しない。** 呼びたくなったら `index.js` の口に足すか、
そもそも時系列の仕事かを考え直す。

例外は `kinds.js` で、**2箇所が直に見ている。**
`store.js` は循環を切るため（`index` → `view` → `store` になる）。
`detail-panels.js` は `splitEdits` を使うためで、あれは `index.js` の口に無い
（時系列の語彙だが、パネル側でも同じ分け方が要る）。

**循環を切っている所が4つある。動かすと立ち上がらない。**

| 切り方 | 切っている循環 |
|---|---|
| `hideQueryValue` は隠す種類を引数で受け取る | `store` → `kinds` → `store` |
| `store.js` は `timeline/kinds.js` を直に見る（`index.js` を経由しない） | `index` → `view` → `store` |
| `detailErrorNow` は `rows.js` に置く | `detail` ⇄ `session` |
| `setListOpen` は `drawer.js` に置く | `list` → `main` → `list` |
| 拡大は `zoom.js`（層2）に置き、組み直しは `initZoom({ onChange })` で差す | `detail` ⇄ `zoom` |

実行の台帳も同じ形で切ってある。**`runs.js`（層2）は描画側を知らない。**
`subscribeRuns(fn)` で外から登録し、配線するのは `main.js`（層8）。
`runs.js` が `run-view.js` を import すると `runs`(2) ⇄ `run-view`(3) の循環になる。

配るのは**台帳が動いたときだけ。** 現れた・状態が変わった・終わった・許可を訊かれた
（または答えた）・設定を替えた、と枠の使用率が動いたとき → `renderDetailIfNeeded()`。

**速報（`run` の出来事）は1件も配らない。** 画面が1件も持たないから配る中身が無い。
1ターンで数百行来るので、そこで作り直すと開いた `<details>` と入力中の caret が毎回消える。
`detailKeyOf()` に混ぜるのも `runStampFor()`（**出来事が増えただけでは動かない値**）だけ。

**それでも `run` の受け口は残してある。** `takeSeq()` が seq の水位を進めるためで、
つなぎ直しの起点（`/api/runs/stream?from=<seq>`）がこの数そのものになる。
受け口ごと消すと起点が 0 に戻り、切れるたびにリング1000件を送り直させる。

ふるまいで気をつけている所。

- SSE でつなぎ、`apply()` が一覧・まとめを描き直す。詳細は `renderDetailIfNeeded()` を通し、`detailKeyOf()` の値が動いたときだけ作り直す（毎回作り直すと開いた `<details>` と入力中の caret が消える）
- 時系列だけは `Timeline.render()` が `.tl-host` を差し替える。絞り込みの帯は器の外に置く（中に入れると1文字ごとに入力欄が作り直される）
- 描く先は `Timeline.attach()` で預け、`Timeline.detach()` で外す。外から時系列の内部状態を触らない
- 詳細は `detailCache`（`logSize` を印にした8件のキャッシュ）。中身が変わっていなければ取り直さない。印が `0`（不明）なら必ず取り直す
- 取り直しのあいだは `silent` で前の内容を出したままにする
- 作業台の左右の幅は、列の境目のつまみ（`.splitter`）をドラッグして変える。**動かしているあいだ `resize.js` が書くのは生の px 1つだけで、上下限は `base.css` の `clamp()` が持つ。** 窓が狭いときの蓋（`min(…, 40vw)`）も CSS 側なので、窓をリサイズすればその場で効き直す
- 覚えるのは**`clamp()` を通ったあとの幅**（`getBoundingClientRect().width`）。1回のドラッグにつき1回だけ書く。既定へ戻すのは値ではなく削除（インラインの変数と `localStorage` の両方を消す）で、行き先は `base.css` の `:root` に任せる
- つまみは矢印キーでも動く（1回 16px・Shift で4倍）。`Home` と二度押しで既定へ戻る。焦点が見えないと矢印で動くことに気づけないので `:focus-visible` で塗る
- 一覧は**畳める列**。畳むと grid の列が 0 になり、幅が中央へ渡る。閉じているあいだは `inert` で丸ごと触れなくする（幅 0 でも中身は DOM に残るため）
- 狭い画面（860px 以下）だけは**手前に重なる引き出し**（`position: fixed`）。畳んでも中央に渡せる幅が無く、開けば中央が潰れるため。膜もこちらだけ
- **「選んだら閉じる」は重なっているときだけ**（`closeListAfterPick()`）。列のときに畳むと、開けておいた意味が無くなる
- 狭い画面（860px 以下）では右インスペクタが下から出る紙（ボトムシート）になる。**`position: fixed` で浮かせず、grid の同じセルに重ねる。** 幅は列が決めるので二重に書かずに済み、引き出し（`z-index: 40`）と膜（`30`）の階層にも手を出さない
- 画面のモードは `MODES`（`work` / `archive` / `usage`）で照合する。三項演算子で二値に畳まない。`localStorage` には残さない（書庫を開いたまま保存すると、次に開いたとき「誰が待っているか」が見えない状態で始まる）。固定したい人は `?mode=archive` `?mode=usage` でブックマークする
- **数値がタブではなくモードなのは、出す中身がセッション1本のものではないから。** 左のペインは「どのセッションを選ぶか」の場所なので、そこに横断の集計を置くと、選ぶための場所に、選んでいるものと関係のない数字が出ることになる。0.3.0 で配った `?tab=usage` は `initialMode()` が `usage` へ読み替える（**配ったブックマークは切らない**）
- **作業台でないあいだ `apply()` は何も描かない**（`store.mode !== 'work'` で早期 return）。中央も左も消えているうえ、書庫（`/api/archive`）も数値（`/api/usage`）もファイルを開く窓口なので、見えないもののために毎2秒撃たない。左の一覧に触ると、見えていないスクロール位置が毎秒先頭へ飛ぶ。作業台へ戻るときに `setMode('work')` が3つとも追いつかせる
- URL クエリで開き方を指定できる … `?session=<id>` `?theme=dark|light` `?only=1` `?nolive=1` `?mode=archive|usage` `?aq=` `?asort=` `?aproj=` `?adays=` `?tq=` `?hide=`
- **配ったブックマークを切らない。** `initialMode()` が古い形を3つ拾う。`?tab=usage`（0.3.0）→ 数値、`?tab=archive`（0.9.1 まで）→ 書庫、`?mode=board`（監視盤）→ **作業台**。監視盤を書庫へ送らないのは、あれが「どれから手をつけるか」の画面で、その役目を引き継いだのが左の一覧の状態の見出しだから。書庫（過去を探す）は問いがまるごと違う。書き戻す側（`syncQuery`）はもう `?tab=` を出さない
- 数値のパネルは、詳細（`d`）が読めていなくても出す。別の窓口から届くので、詳細の失敗に巻き込む理由が無い
- **数値と中央値は `detailKeyOf()` の材料に入れる。** 入れないと、遅れて着いても鍵が動かず画面に出ない。中央値は有無だけでは足りず（5分ごとの引き直しで中身が動いても鍵が同じになる）、オブジェクトそのものも比べられない（毎回別の参照で届く）。実際に出している値だけを1本の文字列にして混ぜる
- 窓口ごと無いと分かったら一度で諦める（更新の前後で、画面だけ新しくサーバーが古いことがある）。404 の切り分けは**理由が JSON で返るかどうか**。返るならセッションが無いだけ、返らないなら窓口ごと無い
- **中央値が取れなくても何も言わない。** 差は添え物で、無くても数値は読める。ここでエラーを出すと、数値パネルの主役（何が文脈を食っているか）から目が逸れる
- `?hide=` は「キーが無い」と「空で付いている」を分けて見る。空は「何も隠さない」の指定なので既定に戻さない
- 隠している種類だけは `localStorage` に覚えさせない。開き直したら既定（足跡を隠す）に戻す。覚えさせると、足跡をいちど押して中を見ただけで既定が永久に壊れる
- 種類を隠すときは、その種類だけを数えた省略の目印（`elided`）も一緒に落とす。残すと「20 件を省略しました　足跡 20」の文字だけが並び、隠れていないように見える（実測で窓 120 件のうち 36 件がこれだった）
- **省略は絞り込みのチップに出さない。** 上の通り、出るか出ないかは他のチップ側で決まるので、独立したチップにすると件数が嘘になる。実測では「省略 74」と出しながら1行も出ない状態になっていた（74 件すべてが足跡だけの区間で、足跡は既定で隠れる）。その状態で他を全部隠すと時系列が空になる。目印ごと消す指定は URL に残してある（`?hide=elided`）
- 窓（`TL_FIRST` = 4 で開き、`TL_MORE` = 60 ずつ継ぎ足す）の外にしか無い種類は名前で伝える。足跡は新しい 200 件だけが残るので、古い順で見ていると窓の中に1件も入らないことがある。黙っていると「押しても変わらない」に見える
- 描画にかかった時間は `window.deckPerf()` で見る（目安は `renderDetail` が 50ms 未満、時系列の描き直しが 16ms 未満）。測る入れ物は `perf.js` の1つに保つ（2つに割ると `deckPerf()` が片方しか見えない）
- **16ms の目安が当てはまるのは普通の描き直しまで。** 「続きを出す」で 60件を一気に継ぎ足す回と、絞り込みの語を変える回は元から 17〜35ms かかっている（実測。Markdown 化の前後どちらでも同じ）。ここを直すなら窓の刻みか描き直しの範囲の話で、**測ったあとに「前より遅くなった」と読み替えない**。比べるときは同じセッション・同じ件数・同じ操作で前後を測る
- パレット（Ctrl+K）は**自分では何も決めない。** すでにある窓口（`select` / `setDetailTab` / `setInspector` / `setListOpen` / `openRunForm` / `focusTerminal`）を呼ぶだけの器にしてある。判定を持たせると、画面の押しボタンとパレットで挙動が食い違う
- 設定モーダルは `<dialog>` ＋ `showModal()`。Esc・背面の膜・焦点の閉じ込めがタダで付く。中身は**開いたときに1回だけ**引く。ここを毎秒更新しない
- **モーダルの高さは固定する（`height`。`max-height` にしない）。** 節ごとに中身の量が違うので、中身なりにすると切り替えるたびに伸び縮みし、`<dialog>` の中央配置で上下に跳ねる（実測で 354〜535px・上端が 91px ずれた）。値はいちばん中身の多い通知の節が収まるところに置く
- 設定モーダルの中身は3つ（通知・作業フォルダ・いまの様子）で、**引く窓口も3本に分かれている。** 1つが転んでも他は出る（`load()` / `loadDirs()` / `loadStartup()` をそれぞれ投げっぱなしにする）
- **その3つを1枚に積まない。左で節を選び、右に中身を出す。** 前は9つのかたまりが縦一列で、その中に「保存を押すまで効かないもの」「押した瞬間に効くもの」「そもそも変えられないもの」が同じ顔で混ざっていた。節を分けると、足のボタンを**いま開いている節に効くものだけ**に絞れる
- **節の出し入れは CSS がやる**（`.settings[data-sec]` で絞る）。`settings.js` は `dataset.sec` に名前を書き、押した札の `aria-pressed` を付け替え、足の1行（`SEC_NOTE`）を入れ替えるだけ。JS で出し入れすると、節を1つ足すたびに配線が増える
- **作業フォルダだけ保存の経路が違う。** 足す・消すはその場で効く（`/api/settings/rundirs`）ので、足の「保存」ボタンは通知のぶんだけを送る。**その節では保存のボタンごと出さない**（`settings.css` が `:not([data-sec="notify"])` で隠す）。前は本文の説明文で「その場で保存されます」と打ち消していたが、**形で伝わっていないから文で補うことになっていた**
- **鳴らない理由は足に書かない。** 足の1行は通知の節でしか出ないので、そこだけに置くと他の節から辿り着けない。足には短く（`有効 / 送信 12 / 失敗 0`）、理由は「いまの様子」の節（`#settings-health`）に置く
- **読むだけの節は面を沈めて枠を外す**（`.settings-read`）。押せるものが1つも無いことを、文ではなく面で示す（上のバーで決めた線と同じ）
- **追加欄の Enter は保存ではなく「足す」へ回す。** 見た目を `.settings-text` から借りているのでクラスでは見分けられない。参照（`ev.target === dom.runDirAdd`）で分ける（`run-form.js` が本文欄を分けているのと同じ作法）
- モーダルを `<form>` で囲まない。囲うと入力欄で Enter を押した瞬間に閉じる（保存したつもりで消える）。Enter → 保存は `settings.js` が自分で拾う
- URL の入力欄は常に空で開き、いまの値はマスクして `placeholder` に出す。`****` のような偽の値を `value` に置くと、それをそのまま保存して URL を壊す。空欄＝「変えない」、消すのは「消す」ボタンだけの役目
- 数値の欄も空ならキーごと送らない。サーバー側が「キーが無い＝触らない」なので、そこに乗る
- `.settings` に `padding` を持たせない。持たせるとその余白を押したのが背面を押したのと区別できず、`ev.target === dialog` での判定が崩れる
- 更新の帯は、押したあとの見張りを画面側が持つ。当てる作業はサーバの外（C# の別プロセス）で走り、しかも途中でサーバ自身が落ちて起き直る。「押したのに何も起きない」を捕まえられるのは画面側しかないので、無音で終わらせず `STUCK_MS`（120秒。`server.mjs` の `APPLY_GUARD_MS` と同じ）で必ず時間切れを出す
- 開いた直後にもう1回だけ引き直す（`RECHECK_MS` = 10秒）。ランチャは窓を開けてから更新を確認するので、最初に引いた時点の紙はまだ前回の結果か、そもそも無い
- `/api/update` が 404 のとき（サーバーが古い）だけは、画面側で `outdated` を組む。それ以外の判断はサーバー側に置く

状態ラベルの日本語は画面側に持たない。
`/api/sessions` の `meta.stateLabels`（`STATE_LABELS` そのまま）から引く。
状態を1つ増やすときに直すのは `parse/state.mjs` だけで済む。

**どの状態が「答えないと1行も進まない」かも画面側に持たない。**
行の `blocking`（と表そのものは `meta.stateBlocking`）から引く。
`state === 'needs-answer' || …` の列挙を判定として画面に書くと、状態を1つ足した日に
一覧・詳細・上のバーの3箇所で食い違う（実際にそうなっていた）。

**一覧の `STATE_GROUPS` は例外。** あれは「どの見出しに置くか」の割り当てで、
急ぎかどうかの判定ではない（1つの状態が2つの列に入ることはない、という別の約束の表）。
急ぎの印を付ける側は `row.blocking` を見る。

CSS は `public/css/` に平置き。`index.html` の `<link>` の並びが、そのまま重ね順になる。

**`<link>` の順番を入れ替えない。** CSS は宣言順で勝ち負けが付く。
`narrow.css` は上の全部を上書きするので、必ず最後に読む。
`ask.css` は `run.css` の直後・`markdown.css` の前。あとに置くと、
承認カードの中のプラン本文に対して `markdown.css` の見出しの寸法（実測で決めてある）を
うっかり上書きできてしまう。

`usage.css` も**色を新しく作らない。** 使うのは `--accent`（強調1本）と
`--fg-faint` / `--border-strong`（文脈）だけ。
多色のパレットを足すと `tokens.css` の二重定義（`prefers-color-scheme` 側と
`[data-theme="dark"]` 側）を両方直す義務が生まれる。足さなければただ乗りできる。

`settings.css` は狭い窓向けの指定を自分で持つ（`min()` と、`34rem` のグリッド畳み、`40rem` の左ナビ畳み）。
モーダルの都合を `narrow.css` に散らさないため。

**閾値が2つあるのはわざと。** 34rem は数値の3列が潰れるかどうか、
40rem は左の 9.5rem を引いた残りで長いパスが読めるかどうかで、後者が先に苦しくなる。
どちらも**窓の幅で見てよい**。このモーダルの幅は窓に付いて動く（`min(44rem, 100vw - 2rem)`）ので、
`run.css` に書いてある「器の幅と窓の幅がずれる」問題はここでは起きない。
`<dialog>` の既定は `canvas` / `canvastext` という
別系統の色を使うので、意味トークンで塗り替えないと配色を暗くしてもモーダルだけ白く残る。

ライト／ダーク両対応。
色の値は `--l-*`（明）と `--d-*`（暗）に1回だけ書き、`--bg` などの意味トークンがそこを指す。
画面側は意味トークンだけを使う。

`@media (prefers-color-scheme: dark)` の側には `:not([data-theme="light"])` を付ける。
閲覧側の切り替えが両方向で勝つことを、順序や詳細度に頼らず示すため。
これがあるので `[data-theme="light"]` のブロックは要らない。

### Markdown を描く

Claude の出力はほぼ Markdown 記法で書かれているのに、画面には素の文字で出ていた。
表が `| a | b |` のまま並び、`**` が本文に混ざる。そこを描くための2枚（`md.js` / `md-view.js`）。

**外の道具は使えない。** `marked` も `markdown-it` も返すのは HTML の**文字列**で、
流し込むには `innerHTML` が要る。ログ本文を出す場所なので、そこは譲れない。
依存パッケージを増やさない決まりもある。だから自分で書いてある。

分け方はこのプロジェクトの他所と同じ。**判断（純関数）と I/O（薄い殻）。**

| ファイル | 何をするか | DOM |
|---|---|---|
| `md.js` | 文字列 → ブロックの並び（`parseMarkdown`） | 触らない |
| `md-view.js` | ブロックの並び → 節点（`mdBlocks` / `mdView`） | `document.createElement` だけ |

だから `md.js` は Node から import できて、`test/md.test.mjs` が 59 件通っている。
`parseUpdateState`（判断）と `loadUpdateState`（I/O）を分けたのと同じ形。

**描く記法は9つに絞ってある。** 実測（会話ログの assistant 本文）で数えて決めた。

```
インラインコード / 太字 / コードフェンス / 箇条書き / 番号付き / 見出し / 表 / 水平線
チェックリスト
```

出さないのはリンク（0.2%）・引用（0.3%）・打ち消し（0%）。
シンタックスハイライトも要らない（フェンスの言語指定が 885 件のうち 852 件で「なし」）。
**斜体（`*` 1つ）も読まない。** `*.js` のようなふつうの文字列が斜体に化けるほうが害が大きい。

### チェックリスト（`- [ ]` / `- [x]` / `- [~]`）

**後から足した。** 最初は「0%」で見送ったが、それは数えた場所が違っていた。
**来るのは assistant の本文ではなく、プランの本文とユーザーの指示文。**

| 出どころ | 見つかった件数 | 行数 |
|---|---|---|
| assistant の text（20ログ・2,534件） | 0件 | 0 |
| プランの本文（40ログ・30件） | 1件 | 5 |
| ユーザーの指示文（40ログ） | 15件 | 129 |

承認待ちのプランは**切らずに全部描く**場所なので、そこに素の `- [ ]` が並ぶと、
どこまで終わったのかが読めない。

**印は CSS の `::marker` で出す。** 節点に文字を入れない。理由は3つ。

- 本文を選択してコピーしたときに混ざらない（`.md.is-cut::after` の「…」と同じ理由）
- bullet と同じ場所に入るので、印の無い項目と同じリストに混ざっても本文の左端が揃う（実測で全項目 `left: 588`）
- `list-style` を切って印の位置を自分で作らなくて済む

`::marker` で使えるのは `content` と `color` と `font-*` だけなので、図形は描かずに字を置く。

**記号と色は TODO パネル（`panels.css`）から借りる。** 同じ詳細ペインに並ぶので、
同じ「済んだ」を片方は ✓・片方は別の印で描くと、別の意味に見える。**色は1つも新しく作らない。**

| 記法 | `data-task` | 記号 | 色 | 借り元 |
|---|---|---|---|---|
| `- [ ]` | `todo` | □ | `--fg-faint` | — |
| `- [~]` | `doing` | ■ | `--accent` | `[data-status="in_progress"]` |
| `- [x]` `- [X]` | `done` | ✓ | `--done` | `[data-status="completed"] .st::before` |

**`- [~]`（進行中）は GFM に無い。Claude が独自に書くもの。**
実測1件で、TODO の `in_progress` と同じ意味で使われていた。

**受ける記号はこの4つだけ。** 中を1文字なら何でも通す形にすると、
`- [2] 消す対象の一覧とサイズを記録` のような手順の番号が空のチェックボックスに化ける
（実測4件。ユーザーの指示文）。印の後ろは空白か行末に限る（`- [x]abc` は記法として曖昧）。

**印は `md.js` が本文から剥がす。** 残すと画面に `□ [ ] やること` と二重に出るうえ、
`blocksText`（切る予算と「一致 N 件」の物差し）にも入ってしまう。

**済んだ項目は本文の色を1段落とす**（`--fg-faint`）。**取り消し線は付けない。**
TODO パネルの `.subject` は1行の短い題だが、こちらは長い文が来る
（実測でプランの1項目が「Phase 1: 初期理解 (Excel対象把握 …) — 探偵A/B 完了」）。

**途中で切れた入力が日常的に来る。** `clip()` が「…（以下省略）」を足すので、
`**` が片方だけ・フェンスが閉じていない・表が途中で終わる、が普通に届く。
閉じていない記号はただの文字として残し、閉じていないフェンスは `open` を立てて破線で示す
（言葉は足さない。本文に既に「…（以下省略）」が書かれているので二重に報告することになる）。

**検索の目印（`<mark>`）は装飾の中でも効かせる。** 太字やコードの中に当たった語が入ったとき、
記法を描いたせいで目印が消えると「一致 3 件」と出ているのに画面のどこにも色が付かない。
だから `markUp` / `marked` を span ごとに通す（この2つを層0 の `util.js` へ移したのはこのため）。

**見出しは2段下げる。** パネル側が `h3` を使っているので、本文の `#` をそのまま `h1` で出すと
階層が逆立ちする。見た目の大小は元の段（`.md-h1`〜`.md-h6`）が持つので、6 で頭打ちにしても潰れない。

**段の差は「大きさ」「上の余白」「線の太さ」で付け、h4 以下は色で示す。**
どの段が実際に来るのかを数えた（`~/.claude/projects` の大きい順）。

| 出どころ | 見出しを持つ件数 | h1 | h2 | h3 | h4 | h5 | h6 |
|---|---|---|---|---|---|---|---|
| プランの本文（40ログ） | 30件・全件 | 48 | 267 | 351 | 13 | 0 | 0 |
| assistant の text（20ログ） | 2,534件中 202件 | 13 | 630 | 83 | 0 | 0 | 0 |
| ユーザーの指示文（40ログ） | 40件中 26件 | 77 | 245 | 142 | 17 | 0 | 0 |

**h1〜h3 の3段は揃って来る**（プラン30件のうち28件。1件で最大118個・平均 10,402字）。
h4 はまれ（プラン1件・指示文5件）で、**h5 と h6 は3経路すべてで0件。**
いちばん大事なパネル（承認待ち・切らずに全部描く）に118個の見出しが並ぶので、
段が読めないと流し読みができない。

寸法はこうしてある（実測。本文は 13.44px）。

| 段 | 大きさ | 上の余白 | 下線 | 色 |
|---|---|---|---|---|
| h1 | 18.88px | 36.8px | 2px `--border-strong` | `--fg` |
| h2 | 16.64px | 29.6px | 1px `--border` | `--fg` |
| h3 | 14.88px | 21.6px | なし | `--fg` |
| h4 | 13.76px | 16px | なし | `--fg-muted` |
| h5・h6 | 13.44px | 16px | なし | `--fg-muted` |

**線は上2段だけ。** 全部に引くと本文より罫線のほうが目立つ（118個並ぶプランではより効く）。
h1 と h2 は線の有無ではなく太さで分ける。

**h4 を大きさで押さない。** h3 が 14.88px、本文が 13.44px なので、あいだに置くと h3 との差が
1px しか作れない。数えたときは h4 はまれだったが、13個入っているプランが実物にあり、
h3 の直下に来ると文字だけでは見分けが付かなかった。だから色を1段落として示す。

上の余白は段別に4行で書く。どれも詳細度は (0,2,0) なので、**深い段から浅い段の順に書いて
後を勝たせる**（`.md > .md-hr` と同じ形）。見出しの直後だけは詰める（`.md > .md-h + *`）。
上を空けて下を詰めると、見出しがその下の塊のものだと余白だけで読める。

**頭出しで切ったときは、末尾に残った見出しの線を落とす**（`.md.is-cut > .md-h:last-child`）。
後ろには切り跡の「…」しか来ないので、区切る先の無い線になる（`headBlocks` が末尾の `hr` を
落とすのと同じ理由）。`md.js` ではなく CSS で閉じているのは、あちらを直すと
`headBlocks` のテストに触ることになるため。

描いているのは5箇所。**時系列の頭出しも含む。**

| 場所 | 呼ぶ人 |
|---|---|
| 時系列の頭出し | `timeline/blocks.js` の `bodyText` |
| 「全文」の畳んだ中 | `timeline/blocks.js` の `bodyText` |
| プランの本文（提出したとき） | `timeline/blocks.js` の `planBlock` |
| プランの本文（いまのファイル） | `timeline/blocks.js` の `lineageNodes` |
| 待ちのパネルのプランと最後の応答 | `detail-wait.js` |

**頭出しは切る単位をブロックにする。** 文字数で切ると記法の途中で切れた断片を描くことになる
（`**` が片方だけ残った、表が途中で終わった）。`headBlocks` は予算に収まるブロックだけを入れ、
入り切らない1つは中で切る（表は**見出しの行を予算より優先して**残し、箇条書きは項目ごと落とす）。
末尾に残った区切り線は落とす。後ろには切り跡しか来ないので、区切る先の無い線だけが残る。

**パースは1件につき1回。** 頭出しと「全文」は同じ結果から描く（だから `mdBlocks` の口がある）。
文字列を受ける口しか無いと、1件を2回パースすることになる。

**物差しは1つ（`blocksText`）。** 切る予算も「一致 N 件」も、描いたあとの文字で数える。
片方を素の文字列にすると、画面に出ていない記号まで数に入って両者が食い違う。

**切り跡の「…」は CSS の `::after` で出す**（`.md.is-cut`）。節点にすると、
本文を選択してコピーしたときに混ざる。切ったことを `open` で表さないのも同じ理由で、
あちらは「源のフェンスが閉じていない」の意味だけを持たせてある。

**器は `.md` と `.tl-text` を併せて付ける。** 種類ごとの装飾（`prompt` と `echo` の枠・
`say` と `recap` の色）はあちらが持っているので、`timeline.css` と `run.css` を1行も触らずに済む。
ただし `.tl-text` の `white-space: pre-wrap` をそのまま継ぐと表のセルだけ見え方が変わるので、
`.md` の側で `normal` を明示する（同じ詳細度なので、`markdown.css` を後に読むことで勝っている）。

実測（開発サーバー・時系列 74件）。60件を一気に継ぎ足す描き直しは 23.0〜30.3ms で、
Markdown 化する前の同じ操作が 28.3〜34.5ms。**この操作は元から 16ms を超えている**ので、
目安を超えているのは事実だが、Markdown にしたことによる退行ではない。
パースそのものは 57件・6,483字で 6.7ms（1件あたり 0.12ms）。

**プランの2つは描き方を揃える。** 見比べるために並べているものなので、
片方だけ Markdown にすると、同じ文でも別物に見える。

高さの上限は**器の側**が持つ（`details.more > .md` が 30rem、`.is-wait .md` が 24rem）。
`.md` 自身に持たせない。どのパネルへ入れても同じに見える、という前提が崩れる。

## 触るときに壊してはいけないこと（画面側）

- **「あなたの番」の見出しを、止まっていない待ちに付けない。** 判定は `row.blocking`（サーバー由来）だけを見る。付ける先は `detail-wait.js` の `headingOf()` と `run-ask.js` の1箇所ずつで、**そこ以外に増やさない**。返信待ちは `row.stateLabel` から「返信待ち — 次の指示を出す」を組む（Claude は応答を返し終えていて、放置しても壊れるものが無い）
- **急ぎの印を新しい色で作らない。** `.panel.is-block` は**太さと見出し1段だけ**。色は既存の `.panel.is-hot` が持つ。新しいトークンを足すと `tokens.css` の二重定義（明るい側と暗い側）を両方直す義務が生まれる。面も塗らない。タブの帯にも足さない（隣のタブの位置が動いて押し間違いが起きる）
- **`is-wait` を `is-block` に置き換えない。** あれは**レイアウトの印**で、`detail.css` の縦積みと `markdown.css` の `.is-wait .md`（24rem の高さ上限）が付いている。返信待ちのパネルにこそ Markdown が入る
- **Markdown を描くのに外の道具を持ち込まない。** `marked` も `markdown-it` も返すのは HTML の**文字列**で、流し込むには `innerHTML` が要る。依存パッケージを増やさない決まりもある。自作の `md.js` ＋ `md-view.js` で通す
- **`md.js` に DOM を触らせない。** あれが Node から import できて 49 件のテストに乗っているのは、`document` を1つも見ていないから。判断（`md.js`）と I/O（`md-view.js`）を混ぜると、画面側で唯一のテストが動かなくなる
- **閉じていない記号を装飾に化かさない。** `clip()` が「…（以下省略）」を足すので、`**` が片方だけ・フェンスが開いたまま、が日常的に届く。装飾として読むと、そこから先が全部太字になる
- **閉じていないフェンスに言葉を足さない。** 本文に既に「…（以下省略）」が書かれている。`.md-pre.is-open` は線を破線にするだけにする（二重に報告することになる）
- **装飾の中でも `markUp` を通す。** 太字やコードの中に当たった語が入ったとき目印（`<mark>`）が消えると、「一致 3 件」と出ているのに画面のどこにも色が付いていない状態になる
- **チェックリストの印を DOM に入れない。** `::marker` で出す（`.md-list li[data-task]`）。節点にすると本文を選択してコピーしたときに混ざる（切り跡の「…」と同じ理由）。`md.js` が印を本文から剥がしているので、CSS 側で出しても二重にならない
- **チェックリストの印を「中を1文字なら何でも」で読まない。** 受けるのは `[ ]` `[x]` `[X]` `[~]` の4つだけ。緩めると `- [2] 消す対象の一覧とサイズを記録` のような手順の番号が空のチェックボックスに化ける（実測4件。ユーザーの指示文）。印の後ろは空白か行末に限る
- **チェックリストの記号と色を新しく作らない。** TODO パネル（`panels.css`）から借りる（✓ と `--done`、■ と `--accent`）。同じ詳細ペインに並ぶので、同じ「済んだ」を別の印で描くと別の意味に見える
- **済んだ項目に取り消し線を付けない。** 落とすのは色だけ（`--fg-faint`）。TODO パネルの `.subject` は1行の短い題だが、こちらは長い文が来る（実測でプランの1項目が「Phase 1: 初期理解 (Excel対象把握 …) — 探偵A/B 完了」）
- **見出しの段の差を大きさだけで付けない。** 上3段は「大きさ・上の余白・線の太さ」、h4 以下は色を1段落とす。h3 が 14.88px・本文が 13.44px なので、そのあいだに h4 を置くと差が 1px しか作れない。実測で h4 が13個入っているプランがあり、h3 の直下に来ると文字だけでは見分けが付かなかった
- **見出しの線を上2段より下へ増やさない。** 全部に引くと本文より罫線のほうが目立つ。**1件で最大118個の見出しが並ぶ**（プランの実測）ので、そこでいちばん強く効く。h1 と h2 は線の有無ではなく太さで分ける（2px `--border-strong` と 1px `--border`）
- **段別の上の余白を宣言順で書き替えない。** `.md > * + .md-h1` から `.md-h` まで、どれも詳細度は (0,2,0) なので**深い段から浅い段の順に書いて後を勝たせている**（`.md > .md-hr` と同じ形）。並べ替えると浅い段の余白が当たらなくなる
- **`.md` 自身に高さの上限を持たせない。** 持つのは器の側（`details.more > .md` が 30rem、`.is-wait .md` が 24rem）。`.md` に持たせると「どのパネルへ入れても同じに見える」という前提が崩れる
- **プランの2つ（提出したときの本文・いまのファイルの中身）は描き方を揃える。** 見比べるために並べているので、片方だけ Markdown にすると同じ文でも別物に見える
- **頭出しを文字数で切らない。** 切る単位はブロック（`headBlocks`）。文字数で切ると記法の途中で切れた断片を描くことになり、`**` が片方だけ残るとそこから先が全部太字になる
- **切る予算と「一致 N 件」の物差しを分けない。** どちらも `blocksText`（描いたあとの文字）で数える。片方を素の文字列にすると、画面に出ていない記号まで数に入って両者が食い違う
- **頭出しの器から `.tl-text` を外さない。** 種類ごとの装飾（`prompt` と `echo` の枠・`say` と `recap` の色）はあちらが持っている。外すと `timeline.css` と `run.css` に同じ指定を書き写すことになる
- **`.md` の `white-space` を省かない。** `.tl-text` の `pre-wrap` をそのまま継ぐと、表のセルだけ畳んだ中と見え方が変わる。同じ詳細度（0,1,0）なので、`markdown.css` を後に読むことで勝っている（`<link>` の順を動かすと崩れる）
- **切り跡の「…」を DOM に入れない。** `.md.is-cut::after` で出す。節点にすると、本文を選択してコピーしたときに混ざる。切ったことを `open` で表さないのも同じで、あれは「源のフェンスが閉じていない」の意味だけを持つ
- **入力欄（`.composer`）を `.detail-pane` の直下から動かさない。** 詳細ペインは `detailKeyOf()` が `contextTokens` を鍵に含むので 2秒ごとに丸ごと作り直される。流れる箱（`.detail-scroll`）の中へ入れると打ちかけの文が消える。**位置は grid の行の入れ替えで作る**（いまは1行目＝ペインの最上部。答えないと進まない待ちをタブ帯より上へ出したので、読む場所と書く場所を隣り合わせにしてある）
- **既定の中央タブは「経過」。** ただしあれは会話ログの全文が要る（`needsDetail`）ので、画面から起こした直後は `effectiveTab()` が「いま」へ倒す。**`store.detailTab` は書き換えない**（URL と戻り先を保つ）。タブの `aria-pressed` も実効タブに合わせる ―― `store.detailTab` で付けると、倒しているあいだ札と中身が食い違う
- **答えないと1行も進まない待ち（`row.blocking`）はタブ帯より上に出す。** 既定が「経過」なので、ここに置かないと止まっていることがタブの向こうに隠れる。返信待ち（blocking でない）は「いま」タブに残す。**両方に出さない**（同じパネルが1画面に2枚並ぶ）
- **時系列の本文予算（`item.js`）と `TL_FIRST`（`view.js`）はセットで触る。** 予算を絞る前に窓を広げると、長い行を12件ぶん組むことになって初回の描画が重くなる。いまは 指示 300字4行・Claude 120字1行・中間報告 240字2行 で、窓が 12 件（実測で初回 9.3〜14.9ms・1行あたり 123px）
- **`?insp=out` は `?dtab=out` へ読み替える。** 成果は右の紙から中央のタブへ戻したが、あの URL は v0.6.0 で配っている（`git tag --contains bedff48`）。`?insp=basics` のほうは **id を `basics` のまま**にしてあるので読み替えが要らない（札と見出しだけ「診断」へ替えた）
- **`timeline/` の中のファイルを外から直に import しない。** 口は `timeline/index.js` の1枚に絞る。例外は `kinds.js`（層0の語彙）で、`store.js`（`index.js` を経由させると `index` → `view` → `store` → `index` の循環になる）と `detail-panels.js`（`splitEdits` が `index.js` の口に無い）の2箇所が直に見ている
- **選択式の質問の submit を質問ごとに置かない。** 1枚のカードに全問を縦に並べて submit は1つ。質問ごとに置くと「1問目だけ送った」という**サーバー側に存在しない状態**を画面が作れる
- **要求カードを `<form>` で囲まない。** 囲むと `textarea` の Enter が送信になる。「進める」を Enter で誤爆させるのがこの画面でいちばん危ない操作なので、送信は Ctrl+Enter だけにする（`run-form.js` の判定と同じ作法）
- **`choices` の鍵は質問文ではなく番号（`q.key`）。** 台帳は質問文を 200 字で切って画面へ渡すので、切れた文字列を鍵にすると長い質問が永久に答えられなくなる。同じ質問文が2回来ても外れない
- **`updatedInput` を画面から送らない。** 送るのは選んだ札（`choices`）だけで、引数を組むのはサーバー。素通しにすると、カードに出したコマンドと実際に走るコマンドを別にできてしまう＝**人が承認したものと違うものが動く**
- **`ask.questions` が無い質問でもカードを出す。** 版が変わって形が読めなくても、本文＋「断る」で出す。出さないと10分の時間切れまで無言で止まったように見える
- **拡大したペインの中身を組み直さない。節点ごと運ぶ。** 「いま」タブには許可要求のカード（`run-ask.js`）と入力欄（`run-view.js` / `run-resume.js`）が入っていて、あれは節点を module-level に1つだけ持ち、「押しても画面からカードを消さない」「`sending` を解くのは `askBlock()` の入口の1箇所だけ」「入力中の caret を消さない」という約束がその1つに紐づいている。モーダル側へ2枚目を組むと**どちらが本物かを管理する話が丸ごと増える**（人が承認したものと違うものが動く事故の隣）。運ぶだけなら DOM の同一性も配線も焦点の控えもそのまま生きる
- **拡大しているあいだの `.deck` は `visibility` で隠す。`display: none` にしない。** あれは中のスクロール位置を捨てるので、閉じたときに一覧が先頭へ飛ぶ。隠すこと自体が要るのは、`.deck` が「子の数と列の数が釣り合う」前提で組んであり、中央のペインが1枚抜けると右のレールが中央の列へずれるため（その姿が膜越しに透ける）
- **高さの上限を外すのは `.zoom` 側の詳細度で。** `markdown.css` の `.is-wait .md`（24rem）と `ask.css` の `.ask > pre`（16rem）を書き換えない。あれは拡大していないときに長いプラン1本で画面が埋まるのを止めている。`.zoom .is-wait .md`（0,3,0）と `.zoom .ask > pre`（0,2,1）が**読む順ではなく詳細度で**勝つので、`<link>` の位置が動いても効き続ける
- **拡大の開閉を旗で持たない。`dialog.open` も見ない。** 判断は「節点が `.zoom-body` に居るか」の1つだけ（`isZoomed()`）。旗を足せば必ず片方が古くなるし、`dialog.open` は閉じる途中で当てにならない（下）。`restore()` も同じ基準なので、何度呼ばれても平気

- **畳むときは「出すのが先、閉じるのが後」。** 逆にすると `display: none` になった `<dialog>` の中でペインを掴むことになり、版面が消えているぶんスクロール位置の戻しが効かない（実測：畳むほうだけ先頭へ飛んだ）。位置を入れる直前に `scrollHeight` を1回読むのも同じ手当てで、読むとそこで計算が確定する
- **パレットに「縮小」を出さない。** `palette.js` の `open()` は「ほかの `<dialog>` が開いていたら開かない」で弾くので、拡大しているあいだパレットは出てこない。出しても選べない項目になる（畳む口は帯のボタン・Esc・×・背面の4つ）
- **`renderDetail()` の `closeZoom()` は DOM を触る前に置く。** あれは組み直し（= `renderDetail` 自身）を呼び返すので、`dom.detail.replaceChildren()` より後に置くと、内側が組み立てたところへ外側がもう一度同じものを足して**空の案内が二重に出る**

- **`.card.is-usage` のシェブロンを grid の列で置かない。** `.card` は `display: grid` だが列を1つしか持たないので、2列目を作ると `.card-top` / `.card-title` / `.card-meta` が横に並ぶ。`grid-row: 1 / -1` も効かない（明示行が1つも無いので `-1` が行1を指す）。`.card` が `position: relative` を持つのは左の状態バーのためで、その枠は `::before` を `content: none` で殺してあるので空いている。絶対配置で右端の中央へ置き、右の padding を 1.7rem にして字と重ならないようにする

- **アイコンを絵文字にしない。形は `icons.js` の1箇所で持つ。** 絵文字は自分の色を持つので `--warn` のような状態色が乗らない（`run.css` の予算切れの印を絵文字にしなかったのと同じ理由）。線を `currentColor` にしておけば置いた場所の字の色を継ぐ。SVG は `innerHTML` を使えないので `util.js` の `svgEl()`（`createElementNS`）を通す
- **アイコンだけのボタンから `title` と `aria-label` を外さない。** 見た目から文字を消しても意味は消さない。触れば名前が出て、読み上げにも残る
- **細かい形は 16px で必ず見る。** 潰れた実測が3件ある。**線で描いた歯車**は歯の高さ 1.9 に対して線の太さが 1.5 あり、内側に 0.4 しか残らずギザギザの塊になる。**横スライダー**はつまみの円と線の隙間が 0.25 しか取れず「多」の字に見えた。**丸に i**（`info`）は点と棒の隙間が 1.4 で、これは辛うじて読める。どれも「線の太さぶんの余白が残らない」という同じ話
- **歯車は塗りで描く**（`gear`）。線で潰れるのは線幅のせいなので、塗りにすれば 16px でも歯車に見える（実測）。塗りの例外は `contrast`（半分だけ塗る）に前例がある。**中心の穴を別の要素にしない。** 塗りの上に線の円を重ねると、円の内側が地の色ではなく歯車の色で埋まる。1本の `path` に穴の輪郭も入れて `fill-rule: evenodd` で抜く
- **枠の使用率をセッションごとに出さない。** アカウント共通の値なので、実行の数だけ同じ数が並ぶうえ「この実行が使った枠」だと読める。出すのは上のバーに1つだけ（`list.js` の `renderRate`）。届く道が実行の stdout（`rate_limit_event`）しか無いのは出どころの都合であって、「その実行の枠」という意味ではない
- **枠の使用率を行から拾わない。** フレームの封筒（`{rows, stats, rate}`）に1つだけ載って来るので、`runs.js` がモジュール変数に受けて `newestRateLimit()` で返す。行を舐めて「いちばん新しいもの」を選ぶ形にすると、実行が履歴から押し出された瞬間に数が消える
- **古い枠の数を今の数の顔で出さない。** `resetsAt` を過ぎた5時間枠は落とし、5分より古い観測には「いつ測ったか」を添える（判断は `runs.js` の `rateView`）。**`resetsAt` は秒**の unix 時刻なので、ミリ秒として比べると必ず過去になって5時間枠が常に消える
- **`util.js` の `tokens()` を数値の画面で使わない。** `if (!n) return null` なので **0 と不明が同じに見える。** `usage-chart.js` の `tokensStrict` を使う（既存の `tokens()` は変更しない。他の表示が一斉に変わる）
- **速報が1件届くたびに詳細ペインを作り直さない。** 1ターンで数百行来るので、開いた `<details>` と入力中の caret が毎回消える。いまは `runs.js` が速報を配らない（`takeSeq()` で水位だけ進める）ので配線の上でも起きないが、`detailKeyOf()` に混ぜるのを `runStampFor()`（出来事が増えただけでは動かない値）だけに保つ
- **速報を溜め直さない。** 画面に出す正本は会話ログ（経過タブ）で、実行パネルが同じものを2通り描いていたのを1本にしたのがいまの形。溜める器を戻すと、溢れの上限・落とした件数の数え・追記の口（`attach` / `render`）・その CSS が芋づるで戻る
- **`run` の受け口と `lastSeq` の水位取りを消さない。** 出来事を使わないからといって受け口ごと消すと、つなぎ直しの起点（`/api/runs/stream?from=<seq>`）が 0 に戻り、**切れるたびにサーバー側のリング1000件を送り直させる**
- **落とした件数を数える器だけ戻さない。** あれは「溜めているものが溢れた」ことを言う数で、溜めない今は数える対象そのものが無い。0 を出すと「取りこぼしが無かった」と読めてしまう（**0 と不明を分ける**）
- **`RunView.attach()` / `render()` を戻すなら器と一緒に。** 追記する先が無いところへ追記の口だけ戻すと、呼ばれても何も起きない関数が残る。`detach()` だけ残っているのは器ではなく**焦点の控え**だから（無いと詳細ペインの作り直しで焦点が `body` へ飛び、入力中に caret が消える）
- **`/api/runs/events` の窓口は、画面が使わなくなっても消さない。** 入口の名前と応答の形は変えない約束があり、`?from=` の穴埋めを受け持つのはこの窓口
- **`runs.js`（層2）から `run-view.js`（層3）を import しない。** 逆向きになる。`subscribeRuns(fn)` で外から登録し、配線するのは `main.js`（層8）。既存の循環4箇所と同じ切り方
- **未応答の許可要求を速報から読まない。** 画面は速報を1件も持たない（溜めていた頃も 400 で溢れたぶんを捨てていた）。**要求を載せると消えて二度と答えられない。** 行（`row.asks`）から読む。`rows` は毎フレーム総入れ替えなので、取りこぼしが次のフレームで自己修復する
- **押しても画面からカードを消さない。** 消す権利はサーバーだけが持ち、画面は `row.asks` から消えるのを待つ。先に消すと、サーバー側で失敗していたときに**「消えたのに答えられていない」**という最悪の状態になる。成功しても `sending` を `null` に戻さないのは同じ理由
- **`sending` を解くのは `askBlock()` の入口の1箇所だけ。この行を消さない。** 成功時に `send()` が戻さない以上、「サーバーが消した」ことを行そのもので確かめる場所がどこかに要る。無いと、答えたあとに来た**次の要求のボタンが無反応になる**（`send()` 冒頭の即 return に食われる。実測。1回リロードすると直るのが目印だった）
- **`await` の後は `sending !== askId` を確かめてから書く。** 返ってくるまでに別のセッションへ移っていることがあり、確かめずに書くと他人の画面へ結果を出す（`run-view.js` の `post()` が `ops.runId !== runId` を見ているのと同じ作法）
- **要求カードを `run-view.js` に足さない。** 行数ではなく**ライフサイクルが違う**。あちらの `ops` は「入力中のテキスト」「開いた `<details>`」「速報の水位」を溜めて作り直しから守る作りで、要求カードは追記されず答えたら消える。混ぜると `applyEnabled()` の `ops.busy || ops.over` に性質の違う4つ目が入り、`setBusy(true)` が要求カードのボタンまで殺すかの判断が毎回要る
- **プラン承認に「承認したまま plan に留まる」道を出さない。** ボタンは `allow` ＋ 行き先のモードを束ねた形にする。`ExitPlanMode` を許可しただけでは plan から抜けないので、分けると「承認したのに書けない」を人が選べてしまう（これが 0.7.1 までの「bash で止まる」の正体）
- **`/mode`（子を殺さず替える）と `/switch`（建て直す）の振り分けは画面がやる。** 子が生きていて替えるのが権限モードとモデルだけなら `/mode`、それ以外は `/switch`。サーバー側の窓口を「どちらもできる1本」にすると、呼ぶ側から見て指示文が要るときと要らないときがある窓口になる。**ボタンの文言は替えず、下の1行だけを差し替える**（押そうとした位置が動かない）
- **要求カードから実行パネルの節点を掴まない。** カードの下に出す案内は**押せない文だけ**にする。`run-view.js` の札を押しに行くと `run-ask.js` → `run-view.js` の向きができて、`RUN_OVER` をあえて重複させている今の切り方が崩れる
- **替える口を実行パネルの中に置かない。** 速報が数百行伸びていた頃、パネルの中に置くと**いちばん替えたい場面（走っている最中）に限って画面の下へ流れて見つからなかった**（実測。0.7.1 の `<details>` がそうなっていた）。速報を外してパネルが短くなったいまも外に出したままにしてある。詳細ペインは作り直されるので、中に置くと入力中の値と開いた窓が消える。いまは入力欄のすぐ上の札（`.composer-now`）が入り口で、中身は `document.body` に付けた `<dialog class="runsw">`。**どちらも詳細ペインの外**なので作り直しに巻き込まれない
- **別の実行へ移ったら替える窓を閉じる。** `<dialog>` はペインの外にいるので、黙っていると開いたまま残る。前の実行の値が入った窓で押すと、**いまの実行にその値が当たる**。閉じるのは `syncOps()` の `ops.runId !== row.runId` の枝と、`composerFor()` が `null` を返す枝の2つ
- **モデルを自由入力だけにしない。** 何を書けばいいのか分からない（実測の指摘）。候補は `/api/runs/options` の `models`（サーバーが一覧から拾った、実際に使われたモデル）で、そこに無い名前は「自分で入力」から渡せる。値の割り方と組み立て（`MODEL_FREE` / `modelOptions` / `modelPick` / `modelValue`）は `runs.js`（層2）に置き、**層3と層7の両方から使う**。それぞれに残すのは入力欄の出し入れだけ
- **実行パネルを詳細（`d`）の中に入れない。** 起こした直後はまだ会話ログが1行も無く、`d` は null。中に入れるとログが出るまで何も出ず、押したのに何も起きていないように見える
- **起こしたセッションを `select(id, 'live')` で選ばない。** `'query'` にする。起こした直後は一覧にまだ並ばないので、`'live'` で選ぶと次の push（2秒後）に `stream.js` の `apply()` が「一覧から消えた」と読んで選択を外し、先頭のセッションへ飛ぶ
- **めったに触らない3つ（モデル・思考量・上限）は畳む。** 毎回書くのは指示欄だけで、あとは既定のまま押すことがほとんど。**畳んだ札には中身を書く**（「詳細設定」のような空の名前にすると、開かないと分からなくなる）。上限は金が減る話なので、既定のままでも必ず出す
- **権限モードは畳まない。** ここは危ないほうへ倒せる唯一の欄で、`bypass permissions` を選ぶと何も確認せずに走る。**畳む基準は「触る頻度」だけでなく「間違えたときの重さ」も見る**
- **開くたびに畳んだ状態へ戻す。** 前に開いたかどうかを覚えると、起こすたびに違う高さの画面が出る
- **上端を固定して、下だけ伸ばす**（`margin-top` を置いて `margin-bottom: auto`）。畳みを開くと中身が 120px 増える。`<dialog>` の既定（`margin: auto`）は中央に置くので、その半分だけ上端が動き、押す位置も一緒に動く（実測で 60px）。設定モーダルは高さそのものを固定してあるが（節ごとの差が小さいので空白が出ない）、**結果はどちらも「上端が動かない」で同じ**
- **絵は「読み飛ばすな」の場所に置く。** 警告と、危ない権限モードの但し書きの2か所。ラベル3つ（作業フォルダ・最初の指示・権限モード）にも置くが、**グリッドの中（モデル・思考量・上限）には置かない**。絵が縦に何個も並ぶと、いちばん読ませたい警告が「並んでいるうちの1つ」になる
- **危ない権限モードは色だけで伝えない。** 但し書きに三角を出すのに加えて、選ぶ欄そのものの枠も赤くする（`is-danger`）。畳みの下を見ているあいだ、但し書きだけだと欄の状態が視界から外れる
- **`[hidden]` で出し入れするものに `display` を素で書かない。** `[hidden]` のブラウザ既定（`display: none`）は詳細度 0,1,0 しかない。`.runform-danger.has-icon` のような 0,2,0 を素で書くと `display: flex` が勝ち、**`plan mode` を選んでいても「何でも実行します」が出たままになる**（実測）。`:not([hidden])` を付けて逃げる
- **起こした直後に画面を勝手に動かさない。** モーダルを閉じて詳細ペインへ飛ばすと、会話ログが出るまでの数秒「このセッションは開けませんでした」を見せることになる。結果はモーダルの中に出して、移るかどうかは押した人に決めてもらう
- **起こすフォームの見た目を新しく作らない。** 中身は設定モーダルのクラス（`.settings-head` / `.settings-body` / `.settings-sec` / `.settings-label` / `.settings-row` / `.settings-hint` / `.settings-grid` / `.settings-text` / `.settings-num` / `.settings-select` / `.settings-foot` / `.settings-msg`）をそのまま借りる。あちらのセレクタは `.settings` を親に取っていないクラス単体なので、`.runform` の中でも効く。`run.css` に書き写すのは `.settings` 自身に紐づく4つ（本体・`::backdrop`・`[open]`・幅）だけ。**替える窓（`.runsw`）も同じ借り方**にする（器の4つだけ自前）
- **キー操作の判定にクラス名を使わない。** 見た目を借りている以上、`.settings-text` のような借り先の名前が `run-form.js` に書かれることになる。要素名（`input, select`）で見て、本文欄だけは参照（`ev.target === dom.runPrompt`）で分ける
- **パレットに「止める」「替える」「続ける」を出さない。** どれも子プロセスを畳む（あるいは起こす）操作で、Enter ひと押しで走ってしまう。打った文字で並びが動くので、狙っていないものを実行する事故が起きうる。この3つは実行パネルの押しやすい場所にあるので、そちらで足りる（出すのはモーダルが開くだけの「起こす」と「拡大」、窓が出るだけの「ターミナルを前面に」の3つ）
- **パレットに個別のショートカット（Ctrl+N など）を足さない。** Ctrl+K 以外はブラウザが先に取っているものが多く、奪えないキーを画面に書くと「押しても効かないキー」を案内することになる
- **`exec()` で閉じるのを実行より先に置く。** `<dialog>` は閉じるときに開く前の焦点へ戻すので、焦点を動かすもの（一覧を出す）を先にやると、せっかく移った焦点をこちらが奪う。結果を読ませたいもの（`keepOpen`）だけ閉じずに残す
- **パレットの `scrollIntoView` は、直前がグループ見出しならそちらを寄せる。** `block: 'nearest'` は「見える範囲に入っていれば動かさない」ので、項目そのものを寄せると見出しが上に隠れ、どの群にいるのか読めなくなる（末尾から先頭へ巻き戻ったとき、実測で 28.8px ぶん隠れていた）
- **`applyOptions()` を再描画のたびに当てない。** 詳細ペインは他の理由でもよく組み直されるので、毎回 `defaultMode` と `budget.default` を代入し直すと、選んだモードと予算が黙って既定へ戻る。`ui.filled` で1回だけにして、落とすのは別のセッションへ移ったときだけ
- **狭い画面のインスペクタを別のセルへ置かない。** 単一列の `.deck` に in-flow の子が3つ（`.detail-pane` / `.insp` / `.rail`）あると2列から溢れて暗黙の2行目ができ、レールが画面の下で横倒しの帯になる（段2 で実測）。`grid-area` を明示して1行2列へ押し込む（`.detail-pane` と `.insp` を `1 / 1` に重ね、`.rail` を `1 / 2`）。こうすれば重ねる紙が何枚あっても行は増えない。`position: fixed` で浮かせる手もあるが、そちらはレールの幅を `right: <幅>` として二重に書くことになる
- **ボトムシートに膜を敷かない。** レール（`z-index` を持たない）がその下に潜り、開く口と閉じる口を兼ねているレールの設計が狭い画面だけ崩れる。閉じる口は紙の頭の × と、押したのと同じレールのボタン（`setInspector` はトグル）の2つで足りる
- **`.insp` に `z-index` を付ける。** 重なりの順は DOM の並びでは決まらない。中央の中にあるタブの帯（`.detail-tabs`）が sticky ＋ `z-index: 2` なので、印を付けない紙はその下へ潜り、閉じるボタンの上にタブが透けて出る。grid item は `position: static` でも `z-index` が効くので1つ足すだけで済む
- **紙の出方を `transition` で書かない。** `.insp` は JS が `hidden` で消すので `display: none` から現れ、遷移の1フレーム目が無い。`animation` にすれば `base.css` の `prefers-reduced-motion` が `animation-duration` を潰すのでただ乗りできる
- **書庫を作業台と同居させない。** モードとして分ける（`store.mode`）。同居させると「いまの作業」と「過去を探す」が同じ画面で場所を取り合う。片方を見ているあいだ、もう片方は `archive.css` の `.is-archive` で丸ごと消す
- **一覧で並べ替えない。** `store.rows` はサーバー側が `STATE_RANK` と `idleMs` で並べたものなので、状態が変わる位置に見出しを差し込むだけでよい。比較器を2箇所に書かない（畳んだ監視盤も同じ考えで列へ振り分けていた）
- **状態の見出しとカードは入れ子にする**（`li.group` > `.group-head` ＋ `ul.group-body`）。フラットに並べると sticky の効く範囲が一覧の全体になり、**4本の見出しが上端で積み重なる**（実測）。内側の `<ul>` に入れておけば、次のかたまりが来たときに前の見出しを押し出す
- **「あなたの番」の見出しは 0 件でも残す**（`STATE_GROUPS` の `keepEmpty`）。消すと「見ていない」と「無い」が同じ顔になる。残り3つは空なら畳む ―― 4本とも残すと、静かな日に空の見出しが4本並んで縦の場所を食う
- **見出しの点を自前で描かない。** `.state` の `::before` がすでに点を描いているので、背景で丸を置くと二重になる（実測）。色は `li.group` に置いた `--state-color` を継がせる
- **列に入らなかったぶんは必ず数を出す。** 黙って落とすと、サーバー側が状態を1つ足した日に「一覧の件数と列の合計が食い違う」だけになり、どこへ消えたのか分からない。0 と不明を分けるのと同じ扱いで、行き先（作業台の一覧）まで添える
- **書庫の `.deck` の上書きを `narrow.css` へ写さない。** `archive.css` の `.is-archive .deck`（0,2,0）が、あちらの `.deck` 単体（0,1,0）に詳細度で勝つ。セレクタリストは1つずつ独立に詳細度を持つので、隣に並んでいる `.is-insp-open .deck`（0,2,0）はこの勝負に関わらない。**読む順ではなく詳細度で決まる。** 一度「後から読まれるほうが勝つ」と読んで11行足したが、実測（インスペクタの開・閉の両方で抜いても1列のまま）で不要だと分かって落とした
- **並べる器の `align-items` を既定（stretch）のままにしない。** 枠を持つ札（`.tag`）は上下の border 2px ぶん背が高く、枠の無い置き場所（`.path`）はそのぶん引き伸ばされる。中の文字は上へ寄るので、**その1つだけ字の下に隙間が空いて見える**。`.card-meta` と `.card-stats` は `center` で揃える
- **カードに `height: 100%` を敷いたら `align-content: start` も要る。** `.card` は grid なので、既定のままだと余った縦を各行へ分けてしまい、札や数の字の下に隙間が空く（実測で最大 14px）。上へ詰めて、余りは下にまとめて残す
- **書庫のカードの数値は、一覧の応答に混ぜない。** `/api/archive` は末尾 64KB しか読まないが、集計は先頭から積まないと出せない（「載せられない」）。カードを描いてから `/api/sessions/:id/usage` を**並列に**引いて、届いた1枚だけ差し替える。実測で 30 件を逐次 5.4 秒 / 並列 1.0 秒 / memo 後 0.4 秒。組み直すと読んでいる位置が飛ぶので、`refreshTimes` と同じく中身だけ入れ替える
- **まだ届いていない数値を 0 と書かない。** 器だけ点線で置いて高さを取る（届いたときにカードの背が動かない）。`store.archive.usage` は Map なので「まだ引いていない（`undefined`）」と「引いたが取れなかった（`null`）」を分けられる。数の整形は `usage-chart.js` の `tokensStrict`（`util.js` の `tokens()` は 0 と不明を同じに見せる）
- **絞り込みを外す口は、絞り込みの札と形を変える。** ピル型・`--accent`・絵だけの3つを重ねてある。前は同じ角丸・同じ枠の色で横に並んでいて「もう1つの絞り込み」に見えた。ここは押すと状態が変わる唯一のもので、性質がまるごと違う
- **書庫のカードを押しても作業台へ移さない。** モードは `archive` のまま、詳細ペインの節点を拡大モーダルへ運ぶ（`openZoom()`）。探していた結果がその場で消えるのを避けるため。移るかどうかは押した人が決める（モーダルの頭の「作業台で開く」）
- **`<dialog id="zoom">` が `.app` の外にあることに寄りかかっている。** 書庫のとき詳細ペインを消している `.is-archive .detail-pane`（子孫セレクタ）は運んだ先には当たらない。dialog を `.app` の中へ移すと、書庫から開いたモーダルが空で出る
- **モーダルを開いているあいだだけ `apply()` の早期 return を抜ける。** 書庫に出るのはほとんど終わったセッションだが、動いている最中のものも混ざる。開いて見ているものが古いまま止まるのは、見えないものを描かない話とは別。判定は `isZoomed()`（旗を増やさない）
- **「作業台で開く」は閉じてから移す。** 先にモードを替えると、詳細ペインが dialog の中に居るまま作業台の骨格へ切り替わり、中央が空で出る
- **書庫のカードを新しく作らない。** `list.js` の `buildCard` を export して借りる（`run-form.js` が設定モーダルのクラスを借りたのと同じ理由）。違うのは押されたあとの後始末だけなので、そこだけ差し替えられる形（`buildCard(row, onPick)`）にしてある。`archive.js` が層7 なのはこの借用のため（`list.js` は層6）
- **書庫のグリッドで、空・エラー・「続きを出す」に `.is-wide` を付ける**（`grid-column: 1 / -1`）。付けないと1マスに収まり、画面の左上へ小さく出て見つからない
- **置き場所の候補を画面側で作らない。** サーバが `meta.projects` で渡す（`{ dir, label, n }`）。スラッグ（`projectDir`）は不可逆で、`-` が区切りかフォルダ名の一部かを区別できないため、画面では表示名に戻せない
- **候補を空で上書きしない。** 古いサーバは `meta.projects` を返さないので、`Array.isArray` で確かめてから差し替える。受け取れた日の候補をそのまま残す（0 と不明を分けるのと同じ）
- **候補を組み直すとき、選んでいた値を残す。** 引き直すたびに `<option>` を作るので、素朴に `replaceChildren` すると選択が「すべて」へ戻る。候補に無い値（URL を手で書いたぶん）も 1件足して選べるようにする ―― 黙って「すべて」へ戻すと、絞れているのに欄が「すべて」を指す食い違いになる
- **「絞り込みを外す」は並び順も戻す。** 外したのに大きい順のままだと、外れていないように見える
- **絵は絞り込みの札にだけ置く。** 横に4つ並ぶものは形で見分けられると速い。カードの中には置かない（項目が5つあるので、読む量が増えるだけで探す速さは上がらない）
- **`.archive-grid[hidden]` を書く。** `display: grid` は `[hidden]` のブラウザ既定（0,1,0）に勝つので、消す指定を自分で書かないと作業台にいるあいだも出たままになる
- **`usage.css` の `.is-usage .deck` に `.is-usage.is-insp-open .deck` を並べて書く。** `archive.css` の `.is-archive` とまったく同じ理由で、`narrow.css` があとから読む `.is-insp-open .deck`（0,2,0）は `.is-usage .deck`（0,2,0）に**読む順で勝つ**。(0,3,0) の側を書かないと、右の枠を開いたまま数値へ移った人だけ列が戻る。**逆に `@media` で囲む必要は無い**（タブだった頃は狭い画面の引き出しを壊さないよう 861px 以上に閉じ込めていたが、モードは `.list-pane` を `display: none` で丸ごと消すので、狭い画面でも同じ形で通る）
- **幅の上下限を JS に持たせない。** `base.css` の `clamp()` に任せ、`resize.js` が書くのは生の px 1つだけにする。窓が狭いときの蓋（`min(…, 40vw)`）を JS で測って自分で丸めると、窓のリサイズに追いつかないうえ CSS 側と二重管理になる
- **既定へ戻すときに値を書かない。** インラインの変数と `localStorage` の記録を消すだけにする。両方に既定値を持つと必ず片方が古くなる（版の出どころを増やさないのと同じ理屈）
- **覚えるのは `clamp()` を通ったあとの幅**（`getBoundingClientRect().width`）。生の px を覚えると、端まで引っ張ったときに範囲の外の値が残る（実測で `-556px` / `1888px`）。次に開いたとき捨てるか範囲外を持ち続けるかのどちらかになり、**下限に張り付けていたつもりが既定の幅に戻る**
- **保存した幅を検証せずに当てない。** `localStorage` は人が書き換えられる場所。有限の数でない値が `--list-w` に入ると `clamp()` ごと無効になり、`grid-template-columns` が丸ごと落ちて列が消える
- **つまみを `.deck` の grid の子にしない。** `.deck` は「子の数と列の数が釣り合う」前提で組んである（閉じているあいだ `.insp` は `hidden`）。4つ目を挿すと閉じているときの釣り合いが崩れる。ペインの中に置いて絶対配置する。`z-index` を付けるのは、中央の `.detail-tabs` が sticky ＋ `z-index: 2` で、印が無いと帯の下に潜って上のほうだけ掴めなくなるため
- **つまみを収めるペインのセレクタを `.deck >` で絞らない。** `.deck > .list-pane`（0,2,0）は `narrow.css` の `.list-pane { position: fixed }`（0,1,0）に**詳細度で勝ってしまい**、狭い画面の引き出しが列に戻って重なる。裸の `.list-pane`（0,1,0）にしておけば、最後に読まれる `narrow.css` が勝てる。`.is-archive .deck` の側とは**逆向きの罠**なので、どちらに勝たせたいのかを毎回確かめる
- **狭い画面につまみを出さない。** あちらの一覧は列ではなく手前に重なる引き出し（`position: fixed` ＋ `z-index: 40`）で、幅は `width: min(88vw, 24rem)` が決める。掴む境目そのものが無いので `narrow.css` で `display: none` にする（インスペクタも中央に重ねる紙なので同じ）
- **レールのボタンは絵だけ。** 縦のレールに字を積むと1文字ずつ折り返すか、レールそのものを広げることになる。名前は `title` と `aria-label` が持つ（上のバーの補助3つと同じ流儀）。大きさは `.ibtn` に合わせて 1.9rem
- **一覧の開閉はレール（`.rail.is-left`）が持つ。** 右の「数値・診断」と同じ形・同じ大きさにしてある。前は上のバーのハンバーガーと一覧の帯の × に散っていて、右とは作法も違った。レールへ寄せると、書庫や数値のあいだは `.rail` ごと消えるので、**一覧が無い画面に開閉ボタンだけが残らない**
- **狭い窓では左のレールを出さない。** 2列しか無いところへ3本目の縦帯を置くと読む面が削れる。あちらの入り口は上のバーのハンバーガー（`.list-toggle`）で、`narrow.css` が `inline-flex` へ戻す。引き出しは手前に重なるので、中から閉じる × も同時に戻す。**広い窓ではどちらも `display: none`**
- **開いた状態の正は `.app` のクラス1つ。** レールの `aria-pressed` もハンバーガーの `aria-expanded` も、`setListOpen` が同じ場所から付け替える（旗を2つ持たない）
- **`.deck` の列は4通りを明示して書く。** `.is-list-open .deck` と `.is-insp-open .deck` はどちらも (0,2,0) で読む順に負けるので、両方立っているときの `.is-list-open.is-insp-open .deck`（0,3,0）が要る（`.is-archive.is-insp-open` と同じ形）。狭い窓では `narrow.css` がこの4通りすべてを2列へ落とす（一覧が in-flow から外れるので、列が残ると空の列が居座る）。**左端のレールを足したぶん、4通りとも先頭に `auto` が付く**（子と列の数は開閉のどの組み合わせでも釣り合う。実測で 4/4・5/5）
- **読む幅の上限（`.detail` の 66rem）は面の側に置く。** `.detail-scroll` へ置くと、sticky したタブ帯の負 margin がその幅を基準にしているので崩れる。寄せは中央（左寄せだと畳んだときに余白が右だけへ寄る）。拡大では `.zoom .detail`（0,2,0）で外す

### 数値画面（横断モードと詳細ペイン）

弾ごとに直した記録。**どれも「全幅の器」でだけ起きていた**ことに注意する
（詳細ペインは中央ペインの幅なので、同じ症状が出ない）。

- **`.usage-pane` の床は `--bg`。** ここを宣言しないと地は `body` の `--bg-sunk` になり、`.bar-track` と `.trend-spark` が敷いている同じ色と重なって**溝と折れ線の器が消える**（実測。「棒が短いときでも『ここが全体』と分かるように薄く敷いておく」というコメントが横断側でだけ効いていなかった）。`shareBar` の「残りは溝で示す」もこの床の上でしか成立しない
- **器の `padding-top` を戻さない。** 上の余白は最初の子（`.usage-pane > :first-child`）が持つ。器に持たせると、sticky した節見出しの帯（`top: 0` で padding box の上端に貼り付く）との間にその余白ぶんの隙間が残り、**スクロール中の中身がそこを通って見える**（実測 11px）
- **節の境に線を引かない。帯が境を示す。** 境を実線にする案を試したが、帯の下線との2本が 20px の間に並んで**入れ子の箱に見えた**（実測）。線は1種類（節の中の破線）だけ残して、役割を1対1にする
- **節見出しの帯は横断側だけ（`.is-usage` で絞る）。** 詳細ペインは `.panel` が既に階層を持っていて、そこへ帯を足すと「パネルの中にパネル」に戻る。あちらは帯を持たないぶん破線の境が要る
- **帯の面は視覚のためではなく、sticky で下が透けないために敷く。** 一覧の `.group-head` は沈んだ地の上で `--bg` を敷いて立たせているが、こちらは床そのものを `--bg` へ上げたので同じ手が使えない。見た目の区別は下線と太字が持つ
- **`.bar` は棒も折れ線も同じ5列。** 前は棒が4列（2列目 `1fr`）で折れ線だけ5列に組み替えてあり、両方が交互に来るスキルの節で行の形が揃わなかった。寄せる先が折れ線側なのは、あちらが実測で決めた値だから（2列目 `14rem` は器の高さ `1.5rem` に対して 9.3:1。全幅では 48:1 まで伸びて形が消えた）。**棒の側も上限を持つので、全幅で伸びきる問題が同時に解ける**
- **但し書きは1本も減らさない。** 消すのではなく `.usage-read`（`.settings-read` の借りもの）へ寄せて、面で「読めるが目立たない」段を作る。**上限は面の側に置く** … 中の `p` だけに掛けると、字は 46rem で折り返すのに面だけ器の端まで伸びて帯に見える（実測）
- **`readNote` は1本も残らなければ `null` を返す。** 空の面を置かない
- **畳むのは絵だけ。** 「残り N 件の推移を見る」（`foldBlock`）の中に入れるのは折れ線だけで、注記も表も畳まない。何が省かれたかは畳みの外に残る。並べ替えもしない（棒と絵で順位が食い違うと、同じ節に2つの順序ができる）
- **`foldBlock` と `tableDetails` を1本にまとめない。** あちらは「絵に添える表」で、表を畳むのと絵そのものを畳むのは別の判断。まとめると片方の口に `head` や `rows` を `null` で渡せる抜け道ができる
- **「全 N 件を表で見る」を3つ並べない。** 区別が N の値だけになり、閉じたままではどれがどの表か分からない。中身の名前を入れる（`tableDetails` の第1引数は文字列なので署名は変えずに直せる）
- **無帰属（`shareBar`）をスキルの棒より先に置く。** 実測で全体の 5〜8 割がどのスキルにも紐づかないので、それを言わずに個別の割合だけ並べると、足しても 100% に届かない理由が読めない
- **スキルの棒は「全体に占める割合」で並べる。** 「1回あたり」で並べていたのは `runs` が呼び出し回数だった頃の話で、いまは「使ったセッション数」なので `avg` の意味が変わっている。割合なら、たまたま重い1回が順位を歪めることもない（**母数での足切り（`RANK_MIN_RUNS`）も落とした** … 1本でしか使っていないスキルが実際に重いことは普通にある）
- **`barList` の `value` は長さ、`text` は読ませるため。** 割合のように単位が違うものは `text` で渡す。1つの値に2つの役目を持たせない
- **詳細ペイン側で「呼んだ回数」「1回あたり」を出さない。** 1本の会話ではラベルが途切れて再開する例が実測0件なので、`runs` は常に 1、`avg === ite` になる（＝情報がゼロ）。この会話に占める割合へ差し替える
- **サブエージェントのスキル別は、親の `skills` に足し込まない。** `Task` を1回投げただけの会話が機械的に上位へ来る。分母も子ぶんの合計にして、別の節として読ませる
- **`deltaText` は 1000% を超えたら倍率（`×98`）へ替える。** 「+9687%」は事実だが桁を数えないと読めない（実測：セッションを跨いだ推移で 1本目 70k → 直近 6.9M）。**符号は付けない** … 減った側は比が 1 を超えないので、倍率が出た時点で必ず増加。`+×99` のように印を2つ重ねない
- **`usage.css` のコメントに文を足すときは、閉じ `*/` の位置を確かめる。** 既存ブロックの直前に書き足して `*/` を残したまま新しい文を置くと、そこから次のルールまでがセレクタとして読まれ、**ルールが丸ごと無効になる**（実測で `.usage-pane` の床も padding も効かなくなり、`getComputedStyle` の `backgroundColor` が `rgba(0,0,0,0)` になっていた）
- **節の出し分けは CSS が `data-sec` でやる。** JS は器に名前を書いて `aria-pressed` を替えるだけ（`settings.css` の `.settings-pane` と同じ作法）。**節を1つ足しても配線が増えない**し、節点を作り直さないので開いた `<details>` も閉じない。節の一覧は `SECTIONS` の1行で足せる
- **節ナビの見た目を新しく作らない。** `settings.css` の `.settings-navb` を借りる。選んでいないあいだは面も枠も持たず（`border` は transparent）、選んだものだけが `--bg` の面と `--accent` の棒を持つ。帯（`.list-head`）の地が `--bg-sunk` なので、あちらの「沈んだ帯の上で選んだものが浮く」関係がそのまま成り立つ
- **`.usage-nav` に `flex-wrap` を持たせる。** `.usage-head` は折り返すが、その中の `.usage-nav` は別の flex コンテナなので自分で畳まないと横へ溢れる（実測では 360px でも4札が1行に収まったが、札を1つ足せば当たる）
- **開くたび概要へ戻す。** 節を `localStorage` に残さない（モードと同じ扱い。設定モーダルが「開くたびに畳んだ状態へ戻す」のと同じ理由 … 前に開いたかどうかを覚えると、開くたびに違う画面が出る）。節を替えたら `scrollTop` も戻す（前の節の位置が残ると、短い節へ移ったときに何も見えない位置で止まる）
- **概要の「いちばん重いもの」は、行ごとに何で並べているかを書く。** ツールは文脈への積み上がり、スキルは全体に占める割合、セッションは実消費で、**1画面に3つのものさしが混ざる**。書かないと同じ順序で並んでいると読まれる
- **`.usage-head` の `select` に `cursor: pointer` をここだけ足さない。** `<select>` のネイティブ既定が `default` で、書庫（`.archive-head select`）も同じ値を持っている。数値画面だけ変えると、同じ見た目の2つの帯で挙動が食い違う
